# GJS 影像管线可行性验证（2026-11-07）

目的：判断把 Python 后端的影像处理移植到 GJS 是否可行。若可行，扩展就不再需要单独安装后端，可以像普通扩展一样从商店一键安装。

## 结论

**可行。** 影像管线（含 glyph 底板与 SVG 光栅化）已全部实现并逐像素比对：几何完全一致，像素差异仅限抗锯齿边缘，性能可接受。

## 原型

两个脚本，合起来覆盖全部分支：

```sh
# 非 glyph 路径（artwork / plate-rect / plate-circle / plate-rounded 的缩放合成）
gjs -m tools/prototype/gjs-render.js <源图.png> <输出目录> <类别> 0.83 0.7

# glyph 路径（圆角底板 + 渐变 + 投影 + 高斯模糊 + 自适应明暗）
gjs -m tools/prototype/gjs-render-glyph.js <源图.png> <输出目录> 0.83 0.7
```

## 实测结果

样本：6 个图标 × 3 个类别（artwork / plate-rect / plate-circle）× 9 档尺寸（16–512 px）。

| 指标 | 结果 |
| --- | --- |
| **占比偏差** | **0.00 px**（全部 54 组） |
| 平均像素差 | 1.15 – 7.18 / 255（0.5% – 2.8%） |
| 最大差异像素占比 | 12.9% – 38.6%，集中在 16–48 px 的边缘 |

### glyph 路径

用同一个 DeepSeek Harness 图标（浅色底板 + 深色字形）实测：

| 指标 | 结果 |
| --- | --- |
| **占比偏差** | **0.00 px**（全部 9 档） |
| 平均像素差 | 0.18 – 2.05 / 255（均值 1.19，比非 glyph 路径更小） |
| 最大差异像素占比 | 8.6%（16 px）→ 0.8%（256 px） |
| 底板明暗判定 | 与 Python 一致（`light`） |

底板渐变、squircle 遮罩、投影偏移与模糊半径均按 `renderer.make_plate()` / `normalize()` 复刻；Cairo 无高斯模糊原语，用可分离高斯核实现（PIL 用的是三次盒式模糊近似，两者在柔和投影上视觉等价）。

### SVG 源图

SVG 不需要单独方案：现有后端就是用 `GdkPixbuf.Pixbuf.new_from_file_at_scale(path, 1024, 1024, True)` 光栅化，GJS 调**同一个 API**，结果按构造相同。

实测（同一个 btop.svg，1024×1024 光栅化后逐像素比较）：**最大差 0、平均差 0.0000、不同像素 0.0000%**。

完整管线覆盖清单中的全部 7 个 SVG 源图、4 个类别：

| 类别 | 图标 | 最大占比偏差 | 平均像素差 |
| --- | --- | --- | --- |
| artwork | Foliate | 0.00 px | 4.89 |
| artwork | Resources | 0.00 px | 3.99 |
| artwork | Flatseal | 0.00 px | 4.09 |
| glyph | mini.xterm | 0.00 px | 1.47 |
| plate-circle | mpv | 0.00 px | 5.31 |
| plate-rect | btop | 0.00 px | 1.05 |
| plate-rect | nvtop | 0.00 px | 1.10 |

合计：**最大占比偏差 0.00 px，平均像素差 3.13/255**。

### 重采样：必须自己实现 Lanczos，且必须预乘 alpha

Cairo 只有 HYPER/BILINEAR，与 PIL 的 LANCZOS 差异足够大，会连带影响"测量-校正"循环的收敛结果。实测对比（16 图标 × 9 尺寸 = 144 组）：

| 实现 | 超标组数 | 最差平均像素差 |
| --- | --- | --- |
| Cairo HYPER | 15 | 48.98 |
| 自实现 Lanczos3 | 11 | 17.95 |
| **自实现 Lanczos3 + alpha 预乘** | **0** | **7.09** |

**预乘是关键**：PIL 在缩放 RGBA 时先乘 alpha、缩放后再除回。不预乘的话，透明区域的黑色 RGB 会渗进不透明边缘，边缘发暗。判据很直接——对一个"透明底上的纯红方块"缩放后，PIL 的边缘像素仍是纯红（R≈255）只是 alpha 降低；不预乘的实现边缘 R 会等于 alpha。

16 px 单独放宽到 12/255：此时底板只有 9–13 px 宽，1 px 取整就是 8% 的图像面积，定点循环在该尺度上本质混沌。

### 移植时必须保留的两个细节

Python 的 `round()` 是**银行家舍入**（.5 取偶），JS 的 `Math.round()` 是向上取整。放置偏移在部分尺寸上正好落在 .5，导致 1 px 错位。

在 32 px 上实测：修正前偏移 `+1.00,+1.00`、不同像素 38.7%；修正后偏移 `0.00`、不同像素 19.8%。

原型里的 `pyRound()` 已复刻该行为。**移植时必须保留这个细节**，否则每个图标在部分尺寸上会偏 1 px。

#### 2. glyph 的测量对象是"只有字形"的图层

`normalize()` 里 `measured = analyze(layer)` 测量的是**仅含字形的图层**，底板和投影是在循环结束后才合成上去的。

原型第一版把底板一起算进了测量，16 px 上立刻偏离（`measured=13, desired=9`）。改为单独测量字形层后 9 档全部收敛到 `err=0`。**这是移植时最容易踩的坑**：底板会主导 `source_ratio`，让校正循环朝错误方向收敛。

### 性能

| 实现 | 一个图标 9 档 |
| --- | --- |
| Python（numpy + PIL） | 0.03 s |
| GJS（GdkPixbuf + Cairo） | 0.055 s（已扣除约 0.026 s 的启动开销） |

GJS 约为 Python 的 1.8 倍。按 74 个图标计约 4 秒，且这发生在**设置进程**而非 Shell 主线程，不会阻塞桌面。

## 移植规模的重新估算

后端现有 5122 行，其中影像核心只有 442 行（`analyzer.py` 241 + `renderer.py` 201）。

但转 GJS 后**以下部分会整体消失**，因为不再有跨进程边界：

| 模块 | 行数 | 去向 |
| --- | --- | --- |
| `control.py`（协议分发） | 916 | 改为内部函数调用 |
| `protocol.py` | 304 | 不再需要 |
| `service_control.py` | 167 | 不再需要 systemd 单元 |
| `config_store.py` | 173 | 改用 GSettings |

净代码量可能持平甚至更少。真正的新增工作是影像核心的 GJS 版本（约 600 行，含 glyph 路径）。

## 主要风险

1. **Shell 主线程不能做图像计算** —— 必须放在设置进程或 worker 里，否则会卡桌面。
2. **首次生成需要时间** —— 74 个图标约 4 秒，需要后台异步 + 进度提示。
3. **Cairo 无 Lanczos** —— 只有 HYPER/BILINEAR；本验证显示视觉差异可忽略，但属于有意的取舍。
