# GJS 影像管线可行性验证（2026-11-07）

目的：判断把 Python 后端的影像处理移植到 GJS 是否可行。若可行，扩展就不再需要单独安装后端，可以像普通扩展一样从商店一键安装。

## 结论

**可行。** 几何结果完全一致，像素差异仅限抗锯齿边缘，性能可接受。

## 原型

`tools/prototype/gjs-render.js` —— 用 GdkPixbuf + Cairo 复刻 `analyzer.analyze()` 与 `renderer.normalize()` 的非 glyph 路径：

```sh
gjs -m tools/prototype/gjs-render.js <源图.png> <输出目录> <类别> 0.83 0.7
```

## 实测结果

样本：6 个图标 × 3 个类别（artwork / plate-rect / plate-circle）× 9 档尺寸（16–512 px）。

| 指标 | 结果 |
| --- | --- |
| **占比偏差** | **0.00 px**（全部 54 组） |
| 平均像素差 | 1.15 – 7.18 / 255（0.5% – 2.8%） |
| 最大差异像素占比 | 12.9% – 38.6%，集中在 16–48 px 的边缘 |

### 唯一发现的系统性偏差

Python 的 `round()` 是**银行家舍入**（.5 取偶），JS 的 `Math.round()` 是向上取整。放置偏移在部分尺寸上正好落在 .5，导致 1 px 错位。

在 32 px 上实测：修正前偏移 `+1.00,+1.00`、不同像素 38.7%；修正后偏移 `0.00`、不同像素 19.8%。

原型里的 `pyRound()` 已复刻该行为。**移植时必须保留这个细节**，否则每个图标在部分尺寸上会偏 1 px。

### 性能

| 实现 | 一个图标 9 档 |
| --- | --- |
| Python（numpy + PIL） | 0.03 s |
| GJS（GdkPixbuf + Cairo） | 0.055 s（已扣除约 0.026 s 的启动开销） |

GJS 约为 Python 的 1.8 倍。按 74 个图标计约 4 秒，且这发生在**设置进程**而非 Shell 主线程，不会阻塞桌面。

## 尚未覆盖

| 项 | 说明 |
| --- | --- |
| `glyph` 路径 | 需要实现 `make_plate()`（自适应底板 + 阴影 + 高斯模糊）与 `superellipse_mask()` |
| SVG 源图 | 现有后端经 GdkPixbuf 处理，原型只验证了 PNG |
| 其余 I/O | 见下 |

## 移植规模的重新估算

后端现有 5122 行，其中影像核心只有 442 行（`analyzer.py` 241 + `renderer.py` 201）。

但转 GJS 后**以下部分会整体消失**，因为不再有跨进程边界：

| 模块 | 行数 | 去向 |
| --- | --- | --- |
| `control.py`（协议分发） | 916 | 改为内部函数调用 |
| `protocol.py` | 304 | 不再需要 |
| `service_control.py` | 167 | 不再需要 systemd 单元 |
| `config_store.py` | 173 | 改用 GSettings |

净代码量可能持平甚至更少。真正的新增工作是影像核心的 GJS 版本（约 600 行，含 glyph 路径）。

## 主要风险

1. **Shell 主线程不能做图像计算** —— 必须放在设置进程或 worker 里，否则会卡桌面。
2. **首次生成需要时间** —— 74 个图标约 4 秒，需要后台异步 + 进度提示。
3. **Cairo 无 Lanczos** —— 只有 HYPER/BILINEAR；本验证显示视觉差异可忽略，但属于有意的取舍。
