# ADR-0007：提交前置状态与持久配置故障

状态：已实现，候选扩展 1.1.6 / 后台 3.1.5，尚未安装或公开发布。

## 所有权前置状态

图标哈希在检查时正确，不代表渲染结束后仍正确。旧路径会在复用时重新读取目标并信任新内容，或在重新渲染时覆盖检查后的外部修改。

`InspectResult.expected_before` 保存本轮读取到的前置 SHA-256，`None` 表示文件当时不存在。范围包括已登记图标、计划输出、受管理启动器、manifest、策略、baseline 和主题索引/标记。它只在内存中传递，不改变 manifest 或事务日志格式。

- 物化再次读取目标时必须匹配前置状态，不能用新内容更新登记哈希。
- `TransactionStore.commit(expected_before=...)` 在计划写入、前置日志持久化后、逐目标写入前、最终检查和缓存更新后验证状态。
- 没有写操作的复用文件仍在检查范围内，不能因不在 changes 中而被漏掉。
- 缺失文件可在首次检查时登记为不存在并按正常路径重建；检查后新出现或消失的目标则返回 OWNERSHIP_CONFLICT。
- 清理和还原同样携带前置状态，不能删除在计划之后发生的外部编辑。

事务运行中失败时，进程把本轮尝试过的操作写回同格式日志，再按原有哈希保护恢复。未尝试写入的文件不参与本轮回滚，因此它们上面的外部修改得到保留。一次替换已成功但 fsync 报错的目标也属于尝试过的操作。

如果外部进程又修改了已尝试写入的目标，恢复仍会拒绝覆盖，并保留日志供后续处理。发生崩溃时，现有恢复检查同样不猜测外部内容。没有新增强制恢复或采纳哈希入口。

这些检查补齐了检查、渲染、复用和提交之间的检测窗口，但不等同于内核级 compare-and-swap：哈希检查和文件替换是分开的系统调用，不合作写入者仍不受 sync.lock 约束。其他程序应把原始图标写入 hicolor，不直接写 DockNormalized；本变更不声称提供对任意外部进程的绝对互斥。

## 持久配置故障

`theme-follow.json` 读取、路径或格式失败时，仍使用既有 INVALID_CONFIG / exit 2，details 增加 `reason=PERSISTED_CONFIG_INVALID` 和文件名。不会自动重置用户文件。

只读 status 直接检查并返回该故障，即使后台尚未运行；不为查询创建健康记录。后台维护或 theme.sync 失败时，将带该原因的 INVALID_CONFIG 纳入维护健康记录，保留首次/最近时间与次数。普通用户输入错误仍不污染健康状态。

status 保留匹配持久记录的首次时间和次数。文件被修复后，旧故障仍保留到完整维护成功；前端沿用已有 last_error → “维护受阻”路径，不需要新增显示协议或错误码。

## 验收

- late writer：复用、重渲染、删除、首次输出碰撞、提交前变更、清理、还原、前置日志写入期间、逐文件写入期间、缓存更新期间。
- 失败时保留外部字节、原登记及上次成功时间；仅本轮已尝试操作回滚。
- 无变化维护仍为零文件操作，既有格式可直接升级。
- 损坏 JSON、错误结构/字段类型、只读诊断、重复失败计数、配置修复后完整维护解除、普通输入校验隔离。
- 前端在上次维护成功且策略未过期时，仍对持久配置错误显示受阻。

本轮在私有 HOME/主题与独立 systemd 测试管理器中验收，不对真实安装注入故障。
