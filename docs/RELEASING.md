# 版本与发布规则 / Versioning and releases

本文件把 `CONTRIBUTING.md` 里「文档维护不需要重打版本标签」这条约定写成可执行规则，并说明什么时候才该递增版本。

## 版本号的含义（语义化版本）

| 位 | 什么时候递增 | 例子 |
| --- | --- | --- |
| **MAJOR** `x.0.0` | 破坏兼容：协议操作被删改、配置格式不兼容、旧后台无法与扩展共存 | 删除某个 `operation`、改 `rules.set` 的参数语义 |
| **MINOR** `1.x.0` | **新增用户可感知的能力**，旧用法仍然有效 | 新增 `plate-rounded` 类别、规则页可编辑逐图标规则、规则失效通知 |
| **PATCH** `1.1.x` | **修复用户可感知的错误**，不新增能力 | 孤儿图标没被清理、重置规则没清覆盖、类型错误导致构建失败 |

**测试、文档、CI 脚本、质量门、重构**：不递增版本。它们随下一个真正的发布一起走。

## 一次发布 = 一个用户可感知的结果

发布说明写给用户看，所以一次发布应当能用一句话说清「用户会看到什么变化」。
同一批工作里的多个内部步骤（写测试、改文档、修 CI）不应各占一个版本号。

反例（本项目真实发生过）：一次持续改造拆成 43 个 patch 版本，其中 13 个是纯文档、10 个是工具脚本，
只有 3 个是真正的 bug 修复。用户看到 `1.1.51` 会以为经历了 43 次修复，实际只有 1 次功能发布。

## 递增版本时要同时做的事

1. `extension/metadata.json` 的 `version-name`；
2. `backend/icon_normalizer/version.py` 的 `BACKEND_VERSION`（渲染算法变化时同时递增 `CORE_VERSION`）；
3. `pyproject.toml` 的 `version`（必须与 `BACKEND_VERSION` 相同，否则 Q5 失败）；
4. `CHANGELOG.md` 新增一节，并写 `docs/RELEASE-<version>.md`；
5. `docs/README.md` 的「最新发布」指向新版本；
6. `docs/HANDOVER.md`、`docs/CHECKLIST.md`、`docs/REVIEWER-NOTE.md` 的头部版本；
7. 跑 `bash tools/verify.sh`，然后 `python3 tools/install.py --assume-yes`。

第 1–7 步分别由 Q5、Q14、Q15、Q16 自动校验；漏掉任何一项都会让验证失败。

## 自动检查

| 门 | 检查 |
| --- | --- |
| Q5 | `pyproject.toml` 与 `BACKEND_VERSION` 一致 |
| Q14 | 已安装的后台代码与仓库逐文件一致 |
| Q15 | 已安装的扩展与仓库逐文件一致 |
| Q16 | 三份文档头部与索引都指向当前版本 |
| **Q17** | **只改了文档的提交不得递增版本**（`CONTRIBUTING.md` 第 30 行的机器化） |

## 已经发布过的版本号不要回收

即使版本号起得不好，也**不要**回头改写已推送的版本。历史版本号是升级路径的一部分：
用户机器上可能装着旧版本，扩展商店也按版本号判断「是不是新版本」。

正确的做法是**向前修正**：下一个发布用正确的号，并在本文件里留下记录。

### 本项目的处理

2026-11-06：`1.1.9`–`1.1.51`（43 个 patch）代表的工作合并发布为 **`1.2.0`**。这些中间版本从未上传到扩展商店，也没有用户安装过，因此不构成升级路径问题。此后按本文件的规则递增。
