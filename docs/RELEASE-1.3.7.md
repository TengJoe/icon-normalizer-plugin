# Icon Normalizer v1.3.7

发布日期：2026-11-10。扩展 **1.3.7**、配套后台 **3.1.20**，支持范围为已测试的 **GNOME Shell 51**。

## 修复：应用时只有一句"正在处理图标…"，看不到进展

用户反馈："应用的时候等待了很久"。实测后确实如此，但**耗时是真实的，界面没有告诉他进展**。

### 实测数据（本机 85 组图标、768 个受管文件）

| 场景 | 耗时 | 说明 |
| --- | --- | --- |
| `status` | 3 ms | 读状态 |
| `scan` | 322 ms | 计划一次 |
| 增量 `apply` | 557 ms | 只有 10 个文件变化 |
| **全量重渲** | **约 23 s** | 换源主题后所有图标输入都变了 |

单图标成本（512px 源，9 个尺寸 + PNG 编码）实测 **266 ms**，其中 16px 从 512px 降采样最贵。

### 原因

源主题从 `Yaru` 跟随为 `Yaru-blue-dark` 后，每个图标的 `input_key` 都变了，缓存全部失效 —— 这是一次**不可避免的全量重渲**。问题不在耗时，而在**界面全程只有一句静止的"正在处理图标…"**。

### 修复：按图标上报真实进度

渲染阶段按图标回报进度，面板显示 `正在处理图标… 42/85`：

- `Engine.inspectGenerator({onProgress})` 在每渲染完一个图标后回调 `{phase, done, total}`；
- `syncAsync()` 与 `sync()` 都接受该回调（切片与非切片路径一致）；
- `LocalControl.apply()` 仅在**进程内**转发回调（跨进程时函数会被 JSON 丢弃，Python 路径不受影响）；
- `runApplyFlow()` 把它放进 apply 信封，面板据此更新标签；离开忙碌态时自动清除读数。

### 验证

- 夹具冷启动：67 图标 → **67 次回调**，首条 `{done:1,total:67}`、末条 `{done:67,total:67}`；
- 切片模式（Shell 实际配置）613 个文件、16.7 s，进度连续；
- 增量路径无渲染任务时**不产生回调**（不显示假的 0/0）。

## 未做的事（已评估）

**提速本身没做**：把 Lanczos 换成 Pillow 的 `reduce` 预处理可以明显加快 16–32px 的渲染，但那会破坏与 Python 的逐像素对拍契约（Q19）。当前取舍是**保 parity，用进度条缓解观感**。
